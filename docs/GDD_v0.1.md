# Dream Form Arena｜Game Design Document（GDD）v0.1

> 文档性质：从《Dream Form Arena｜Steam 产品愿景与完整化路线 v0.1》继续向可开发规格拆解。
>
> 状态标记：
> - **[已定]**：上一层产品愿景已经明确的内容。
> - **[暂定]**：为便于开发而补出的第一版实现规格，可以在试玩后修改。
> - **[待定]**：当前资料不足，不在本版擅自定死。

---

## 0. 文档目标

本 GDD 的目标不是一次写死完整游戏，而是把 Dream Form Arena 从“产品愿景”拆成可以持续开发、测试、扩展的游戏系统规格。

本版重点服务三个目标：

1. **把 Hero 01 与第一段冒险体验纵向做穿；**
2. **保证多形态机制同时进入战斗、探索和事件；**
3. **为后续 8 英雄、完整剧情、PvP 与 Steam Demo 扩展预留统一框架。**

当前不以“所有内容都确定”为目标，而以“核心规则足够清楚，可以开始正式生产”为目标。

---

# 1. 产品定义

## 1.1 一句话定义

**[已定]**

Dream Form Arena 是一款以“一个英雄拥有多个完全不同可玩身体”为核心规则的第三人称动作冒险游戏。玩家通过形态变化改变自己的移动、战斗、探索和事件解法，并在剧情世界与独立 PvP 战场中使用同一套英雄系统。

## 1.2 正式定位

**[已定]**

- 主体：第三人称多形态英雄动作冒险；
- 主内容：PvE 冒险剧情；
- 扩展模式：独立 PvP；
- 核心差异：英雄不是“一个角色 + 一组技能”，而是“一个英雄 + 多个完全不同的可玩身体”。

## 1.3 产品支柱

### 支柱 A｜形态不是技能，是身体

**[已定]**

每个形态必须改变至少四类体验：

- 移动方式；
- 战斗职责；
- 空间使用方式；
- 探索 / 事件解法。

禁止把形态退化成“同一角色换模型、换技能栏”。

### 支柱 B｜同一个机制贯穿 PvE 与 PvP

**[已定]**

英雄基础机制共用，但 PvE 与 PvP 可以使用不同数值与规则配置。

### 支柱 C｜冒险世界必须回应玩家的形态

**[已定]**

地图、NPC、事件、机关和敌人都需要能够识别玩家当前形态，使变形成为世界规则，而不仅是战斗按钮。

### 支柱 D｜短时间内可被看懂的视觉卖点

**[已定]**

宣传和试玩必须能快速呈现：

**本体战斗 → 变化形态 → 另一种战斗逻辑 → 改变战局。**

Hero 01 当前已经具备最直接的展示链：

**火箭炮手 → 绿色冲撞飞碟 → 白蓝控制飞碟 → 吸入敌人并改写为友军。**

# 2. 游戏模式结构

## 2.1 Campaign｜冒险剧情模式

**[已定]**

游戏主体。

玩家：

- 选择英雄；
- 进入区域；
- 探索；
- 与 NPC 互动；
- 触发事件；
- 战斗；
- 使用不同形态处理环境 / 战术问题；
- 完成 Boss 或关键剧情节点；
- 跳转至新地图 / 新区域；
- 解锁后续内容。

## 2.2 PvP｜独立竞技模式

**[已定]**

使用同一英雄与形态体系，但：

- 数值允许独立；
- 冷却允许独立；
- 控制时间允许独立；
- 资源恢复允许独立；
- Boss / 剧情专属能力可关闭或替换。

PvP 不应倒逼 PvE 放弃爽感。

## 2.3 Demo / Vertical Slice｜垂直切片

**[已定]**

目标：20–30 分钟连续体验。

至少需要：

- Hero 01 完整；
- 1 个正式区域；
- 1 套局部剧情闭环；
- NPC；
- 动态事件；
- 普通敌人；
- 至少 1 个精英敌人；
- 1 个 Boss；
- 地图跳转或区域切换；
- 基础成长 / 解锁；
- 正式 UI 与音效雏形。

# 3. 核心游戏循环

## 3.1 宏观循环

**[已定]**

`选英雄 → 进入区域 → 探索 → NPC / 事件 → 战斗 → 形态切换 → 环境 / 战术解法 → Boss / 关键剧情 → 地图跳转 → 解锁新内容`

## 3.2 单场战斗循环

**[暂定]**

`观察战况 → 选择当前最适合的身体 → 建立优势 → 触发 / 满足变化条件 → 切换形态 → 改变空间关系 → 收割 / 控场 / 脱离 → 再评估`

核心不是连招长度，而是：

> **“什么时候换身体”本身就是玩家决策。**

## 3.3 探索循环

**[暂定]**

`发现阻碍 → 判断可用形态 → 使用移动 / 扫描 / 控制 / 破坏能力 → 打开路径 → 获得信息 / 资源 / 新事件`

## 3.4 事件循环

**[暂定]**

`发现事件 → 识别参与对象 → 选择英雄 / 形态 / 对话 / 行动方式 → 世界状态改变 → 产生后续结果`

事件不要求每次都做复杂分支，但必须让部分事件能明显感受到“形态不同，解决办法不同”。

# 4. 英雄系统总则

## 4.1 英雄基本单位

**[已定]**

每名英雄至少包含：

- 1 个基础形态；
- 2–3 个变化形态。

完整 8 英雄意味着约 24–32 个可玩形态。

## 4.2 形态设计最低要求

**[暂定]**

任何新形态在立项时必须填写以下六项：

1. **身体轮廓：** 它看起来和其他形态是否一眼不同？
2. **移动：** 它如何改变位移与空间使用？
3. **攻击：** 它的主要输出方式是什么？
4. **职责：** 爆发 / 破阵 / 控制 / 防御 / 侦察 / 召唤 / 其他？
5. **探索：** 它能做基础形态做不到的什么？
6. **事件：** 世界或 NPC 是否会因这个形态产生不同回应？

缺少其中 3 项以上，不应被视为完整变化形态。

## 4.3 形态切换原则

**[暂定]**

切换系统优先满足：

- 快速；
- 可预测；
- 不打断玩家理解；
- 有战术意义；
- 不要求频繁进菜单。

形态切换不应成为纯粹 CD 技能；它更接近“改变角色状态空间”。

## 4.4 形态状态继承

**[暂定]**

统一设计建议：

### 继承

- 当前阵营；
- 任务状态；
- 世界交互状态；
- 目标锁定的语义对象；
- Hero 级 Buff / Debuff（除非能力明确说明）。

### 可独立

- 形态能量；
- 形态技能冷却；
- 形态特殊资源；
- 形态专属移动状态。

### 生命值

**[待定]**

需在正式 PvE 战斗测试后决定：

- 共用生命值；
- 按形态独立生命值；
- 主生命值 + 形态护甲层。

当前不锁死。

# 5. Hero 01｜火箭炮小人

## 5.1 英雄定位

**[已定]**

Hero 01 是 Dream Form Arena 第一个纵向打穿的英雄，也是第一支 Steam 宣传片 / Demo 的核心展示英雄。

变化逻辑：**身体变形。**

当前三个形态：

1. 基础火箭炮手；
2. 绿色冲撞飞碟；
3. 白蓝战术飞碟。

## 5.2 Hero 01 的整体设计目标

**[暂定]**

Hero 01 必须让第一次接触游戏的玩家在 5–10 分钟内理解：

> “这不是普通英雄技能组，而是三个不同身体组成的一个英雄。”

三个形态应形成清晰三角：

- **基础形态：射击 / 通用；**
- **绿色飞碟：突破 / 高机动 / 近身冲撞；**
- **白蓝飞碟：控制 / 战术 / 单位改写。**

---

## 5.3 基础形态｜火箭炮手

### 战斗身份

**[已定]**

- 第三人称射击；
- 火箭弹；
- 爆炸伤害；
- 击退；
- 当前原型已经采用屏幕中心准星 → Camera Ray → AimPoint → Muzzle 的瞄准链。

### 移动

**[暂定]**

作为 Hero 01 的“标准身体”，承担：

- 最稳定的地面移动；
- 最清晰的 TPS 操作；
- 最适合精确选择目标的位置。

### 战斗职责

**[暂定]**

- 中距离范围伤害；
- 制造击退；
- 软化敌人；
- 为绿色飞碟创造冲撞路线；
- 为白蓝飞碟创造可捕获 / 可控制窗口。

### 探索作用

**[待定]**

目前尚未在上层文档中确定基础形态的独有探索能力。

第一张正式地图至少应给它一种非战斗用途，避免“探索时只有飞碟有用”。

---

## 5.4 变化形态 A｜绿色冲撞飞碟

### 战斗身份

**[已定]**

- 高速突进；
- 撞击；
- 破阵；
- 巨大化终极形态 / 大招。

### 现有原型能力

**[已定]**

- 冲撞；
- 巨大化；
- 大体积视觉模型；
- 实际碰撞体小于视觉体积以减少地形卡死；
- 对低矮障碍具有穿越 / 碾压倾向；
- 墙面滑动与基础防卡死处理。

### 设计目标

**[暂定]**

绿色飞碟的核心不是“飞起来打伤害”，而是：

> **把自己变成战场中的高速物理事件。**

玩家进入该形态后，思考重点从“瞄准谁”切换为：

- 从哪里切入；
- 哪条路线能撞最多目标；
- 哪些障碍能破；
- 是否值得巨大化；
- 如何避免撞进死角。

### 探索作用

**[暂定]**

优先考虑：

- 撞碎脆弱墙体；
- 强行开启破坏型捷径；
- 穿越危险区域；
- 巨大化后触发特定机关；
- 以速度完成追逐 / 逃脱事件。

---

## 5.5 变化形态 B｜白蓝战术飞碟

### 战斗身份

**[已定]**

- 控场；
- 牵引；
- 扫描；
- 护盾；
- 收容敌人；
- 认知改写 / 临时转化为友军。

### 现有原型能力

**[已定]**

- 左键：引力锚 / 牵引；
- E：反制护盾 / 减伤与反射；
- F：弱点扫描，制造控制 / 易伤窗口；
- R：同调俘获：升空 → 光波 → 吸入普通 Bot → 转化 → 释放友军；
- 原型暂定友军持续约 12 秒；
- 原型暂定技能冷却约 14 秒。

### 设计目标

**[暂定]**

白蓝飞碟的核心不是“远程法师”，而是：

> **重新定义战场单位之间的关系。**

它应该是 Hero 01 三个形态中最“规则型”的身体。

### 探索 / 事件作用

**[已定 + 暂定细化]**

上层愿景已经明确它可以：

- 扫描特殊目标；
- 控制敌方单位；
- 让被控制单位替自己作战；
- 使用敌方身份进入特定区域；
- 改变 NPC 或敌对阵营事件。

第一段冒险建议至少实现其中 **2 项**，否则白蓝形态仍会停留在纯战斗工具。

# 6. Hero 01 三形态协同

## 6.1 战斗协同

**[暂定]**

### 基础 → 绿色

火箭爆炸把敌人击退 / 聚集到有利位置，绿色形态随后高速冲撞。

### 基础 → 白蓝

先用爆炸削弱普通敌人，再使用白蓝形态进行控制或收编。

### 白蓝 → 绿色

白蓝形态把目标拉到冲撞线路，再切绿色形态破阵。

### 绿色 → 基础

绿色突入敌群后脱离，切回基础形态进行范围轰炸。

### 白蓝 → 基础

收编友军吸引火力，基础形态在远处进行爆炸输出。

## 6.2 设计验证问题

每次 Hero 01 调整都要问：

- 有没有一个形态永远最优？
- 有没有一个形态只是为了放一个技能？
- 切换后玩家的操作逻辑是否真正发生变化？
- 三形态之间是否能形成自然连贯的玩法链？

如果答案倾向“一个形态长期最优”，需要调整。

# 7. 战斗系统

## 7.1 基础战斗框架

**[已定]**

- 第三人称；
- 屏幕中心准星；
- 角色朝向跟随瞄准；
- 右键 ADS（瞄准状态）；
- 投射物 / 爆炸；
- AI 敌人；
- 形态切换。

## 7.2 战斗目标

**[暂定]**

战斗应同时允许：

- 精确射击；
- 位置与路线博弈；
- 形态职责切换；
- 敌我数量关系变化；
- 可破坏 / 可利用环境。

## 7.3 伤害类别

**[暂定]**

首版系统层建议只保留少量语义类别：

- 直接伤害；
- 爆炸伤害；
- 冲撞伤害；
- 控制；
- 易伤 / 标记；
- 反射 / 反制；
- 阵营改写。

不急于增加复杂元素克制表。

## 7.4 控制免疫层

**[暂定]**

敌人至少分为：

- 普通：可完整控制 / 收编；
- 精英：部分控制、缩短时长或增加条件；
- Boss：不能直接收编，但可受到扫描、局部牵引或阶段性机制影响。

避免白蓝形态直接跳过 Boss 设计。

---

# 8. 敌人系统

## 8.1 第一阶段敌人数量

**[暂定]**

首个正式区域优先做 4 类：

1. **普通近战单位**：负责压迫位置；
2. **普通远程单位**：逼迫移动；
3. **重型 / 护甲单位**：给绿色冲撞形态价值；
4. **控制 / 支援单位**：给白蓝扫描与收编价值。

## 8.2 敌人必须支持的语义

每个敌人应暴露：

- 阵营；
- 是否可牵引；
- 是否可扫描；
- 是否可收编；
- 是否可被冲撞；
- 是否可击退；
- 优先目标逻辑；
- 当前控制状态。

## 8.3 收编 AI

**[已定 + 暂定细化]**

转化单位：

- 阵营变为 Ally；
- 主动寻找 Hostile；
- 不默认受到玩家友军伤害；
- 结束后恢复敌方；
- 若死亡则不恢复。

后续可以扩展不同敌人被收编后的独特价值。

---

# 9. Boss 设计

## 9.1 Boss 原则

**[暂定]**

Boss 必须测试玩家是否理解“形态切换”，而不是只测试输出数值。

第一 Boss 至少应设计三个明显窗口：

- 基础形态适合处理的阶段；
- 绿色飞碟适合处理的阶段；
- 白蓝飞碟适合处理的阶段。

## 9.2 禁止做法

- 单纯血量海绵；
- 三形态都能站桩打完；
- 强行锁定唯一技能解法；
- 大量不可读的一击必杀。

---

# 10. 地图与区域结构

## 10.1 区域结构

**[已定]**

完整版拥有多区域与地图跳转。

## 10.2 第一正式区域

**[暂定]**

推荐采用“半开放战斗区域 + 局部线性剧情节点”，而不是直接做大世界。

区域包含：

- 主路径；
- 1–2 条形态专属捷径；
- NPC 安全点；
- 动态事件触发点；
- 1 个战斗竞技场；
- 1 个探索区；
- 1 个 Boss 区；
- 至少一次地图 / 场景跳转。

## 10.3 形态门设计

**[暂定]**

形态门不是传统“钥匙门”，而是：

- 绿色：破坏、速度、冲撞、重量；
- 白蓝：扫描、控制、身份 / 阵营、牵引；
- 基础：射击、精确触发、通用交互。

同一阻碍最好允许至少两种解决路径中的一种，而不是所有谜题都只有唯一按钮答案。

---

# 11. 地图跳转系统

## 11.1 目的

**[已定]**

地图跳转是正式版基础能力之一。

## 11.2 跳转类型

**[暂定]**

首版支持三类：

1. **剧情跳转**：完成关键任务后进入新地图；
2. **节点跳转**：通过门、传送、交通工具进入邻接区域；
3. **回访跳转**：已经解锁区域可重新进入。

## 11.3 跳转需要持久化的数据

- 当前英雄；
- 已解锁形态；
- 任务状态；
- 事件完成状态；
- NPC 状态；
- 玩家成长；
- 重要世界变量。

---

# 12. 事件系统

## 12.1 事件定义

**[已定]**

完整版需要动态事件系统。

## 12.2 事件结构

**[暂定]**

每个事件建议由以下字段组成：

- Trigger：触发条件；
- Context：区域 / NPC / 战斗上下文；
- Preconditions：前置状态；
- Options：玩家可采取的行为；
- Form Hooks：哪些形态能改变事件；
- Result：立即结果；
- State Mutation：世界状态变化；
- Follow-up：后续事件 / 对话 / 奖励。

## 12.3 第一批事件模板

**[暂定]**

### 战斗介入事件

NPC / 敌人正在交战，玩家选择帮助、绕过或利用。

### 路障事件

障碍可以：

- 绿色撞开；
- 白蓝控制某单位开启；
- 基础形态远程触发机关。

### 身份事件

白蓝形态收编敌人后，以对方身份通过检查或改变敌方反应。

### 救援事件

根据形态不同，救援路径不同。

### 追逐事件

绿色飞碟明显占优，但可能失去其他互动机会。

# 22. 教学设计

## 22.1 原则

**[暂定]**

不要用长文字解释“多形态”。

应该通过场景强迫玩家自然发现：

- 基础形态打得稳；
- 绿色形态能解决一个明显障碍；
- 白蓝形态能解决一个基础攻击解决不了的问题。

## 22.2 第一次收编教学

建议设计一个场景：

- 玩家面对多个敌人；
- 正面火力处于劣势；
- 白蓝能力提示出现；
- 收编一个远程敌人；
- 该单位明显转为蓝白阵营并攻击原队友；
- 玩家直观看懂“我改变了敌我关系”。

这是 Hero 01 最重要的 Wow Moment（惊喜时刻）之一。

# 32. v0.1 结论

Dream Form Arena 当前最重要的设计判断已经足够稳定：

- 游戏核心不是单纯 PvP；
- 不是技能堆叠英雄；
- 不是大世界；
- 也不是先做满 8 个英雄。

当前真正要证明的是：

> **一个英雄拥有多个完全不同身体，能否同时支撑战斗、探索、事件和剧情。**

Hero 01 正是这条规则的第一块完整样板。

因此下一阶段的设计和开发，都应围绕 **Hero 01 + 第一正式区域 + 20–30 分钟垂直切片** 收束。

只要这一块成立，8 英雄、完整主线、PvP 和 Steam 正式版才进入可规模化生产阶段。
